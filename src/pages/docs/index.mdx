# Get started with LocalCloud

This tutorial installs the LocalCloud CLI, starts a persistent local runtime, configures this shell, and verifies a Cloud Storage request. LocalCloud runs local versions of Google Cloud services for development and testing. Before you deploy to production, run final validation against real Google Cloud.

## Prerequisites

- Docker Desktop, Colima, or Docker Engine is installed **and running**.
- A supported native CLI host: macOS 13+ or Linux with glibc 2.35+, on ARM64 or AMD64.
- `curl`, `tar`, `sed`, `sort`, and either `sha256sum` or `shasum`.

The CLI is a standalone executable and does not require Python. Windows users should use the [manual Docker fallback](#manual-docker-path).

## Install the CLI

<CodeTabs labels={["Install script", "Homebrew"]}>
  <Fragment slot="tab-0">

```bash
curl -fsSL https://local.cloud/install.sh | sh
```

  </Fragment>
  <Fragment slot="tab-1">
```bash
brew install LocalGCloud/tap/localcloud
```
  </Fragment>
</CodeTabs>

The install script downloads the appropriate macOS or Linux release, verifies its SHA-256 checksum, validates the exact archive members, and runs the executable to confirm its semantic version. Release automation separately publishes Sigstore bundles, but `install.sh` does not verify those bundles.

In an interactive terminal, the installer can offer to run diagnostics and start LocalCloud after you confirm. In automation or with `--no-start`, it prints absolute-path next steps instead. If it adds the CLI to your shell startup file, run the exact `source` command printed by the installer before continuing.

<Callout type="note" title="Check your CLI version">
{docsContract.cli.releaseBoundary}

Run `localcloud --version` before following version-specific instructions.
</Callout>

## Start your first runtime

<Steps>
  <Step title="Check Docker">

```bash
localcloud doctor
```

A usable Docker installation exits successfully and reports `status: ok`. `doctor` diagnoses Docker; it does not install or start Docker Desktop, Colima, or Docker Engine. Add `--verbose` when you need the complete JSON payload.

  </Step>
  <Step title="Start LocalCloud">

```bash
localcloud start --local-only
```

A successful command reports `started`, `already_running`, `restarted`, or
`reconfigured`. Runtime selection precedence is `--data-volume`, the selected
configuration's `host.data_volume`, the active-runtime record, then the
built-in `localcloud-data` fallback. Other built-in defaults are:

- project `local-gcp-project`
- caller `local-developer`
- persistent data
- Docker access mode **auto**: the socket is mounted only when selected services require it; set `host.docker_socket: false` to opt out
- transparent networking **off**
- gateway TLS **off**; enable it explicitly when needed

The example selects `--local-only`, which binds published ports to `127.0.0.1`. Without that flag, the current CLI publishes ports on all host interfaces. Use it again on subsequent `start`, `restart`, and `reset` commands to retain loopback binding. If a default port is already in use,
the CLI can remap host ports. Use `--verbose` to inspect the complete
runtime payload, including immutable container ID, ownership, image identity,
mount details, and `sdk_env`.

  </Step>
  <Step title="Configure this shell">

```bash
eval "$(localcloud env)"
```

`localcloud env` discovers the compatible running container using the selected data volume and prints local-only SDK settings with its actual mapped ports. It rejects environment values that would route supported services to real Google endpoints or non-loopback HTTP endpoints.

  </Step>
  <Step title="Open the console">

```bash
localcloud console
```

The CLI opens the console for the selected runtime, project, and caller. Trust the returned `url`; do not replace it with a hard-coded port.

  </Step>
</Steps>

## Make your first API call

Install the Python Cloud Storage client if needed, then run this repeatable example in the same shell where you evaluated `localcloud env`:

```bash
python -m pip install google-cloud-storage
```

```python
from google.api_core.exceptions import NotFound
from google.cloud import storage

client = storage.Client(project="local-gcp-project")
bucket = client.bucket("localcloud-quickstart")

try:
    bucket.reload()
except NotFound:
    bucket.create()

blob = bucket.blob("hello.txt")
blob.upload_from_string("Hello, LocalCloud!")
print(blob.download_as_text())
```

The example safely reuses the same local bucket and overwrites the same object, so it can run repeatedly with the default persistent volume. The expected output is:

```text
Hello, LocalCloud!
```

If the SDK tries to contact Google Cloud, stop instead of adding real credentials. Re-run `eval "$(localcloud env)"` in the shell or process that launches the application.

## Verify and manage the runtime

```bash
localcloud status --verbose
localcloud logs --tail 50
```
Use `--data-volume NAME` with any runtime command to select an isolated durable
runtime identity and its storage. Without the flag or a configured
`data_volume`, runtime commands use the revalidated active-runtime record before
falling back to `localcloud-data`.
`localcloud stop` stops that selected runtime and retains persistent storage.
`localcloud reset --all-projects` prints manual recreation steps and deletes nothing. The CLI may operate a compatible container created by another tool, but never
removes or relabels Docker resources it does not own. Running the
installer with `--uninstall` removes only a script-managed CLI and its PATH
block; containers and persistent volumes remain intact.

## Manual Docker path

Use this fallback on unsupported CLI hosts or when you deliberately do not want the host CLI. The `latest` tag is mutable, so prefer the CLI for normal use and pin an image digest when repeatability matters.

```bash
docker volume create localcloud-data

docker run -d --name localcloud \
  -p 127.0.0.1:5380-5405:5380-5405 \
  -m 4g \
  -v localcloud-data:/var/lib/localcloud \
  agentcloud/localcloud:latest
```

Verify the runtime and configure the shell through root operator endpoints:

```bash
curl -fsS http://localhost:5380/readiness
eval "$(curl -fsS 'http://localhost:5380/env?format=shell')"
```

The default command does not mount `/var/run/docker.sock` and does not expose ports on every host interface. Docker-backed service execution and custom companion images can require Docker-socket access; transparent DNS/HTTPS routing is also opt-in. Configure those capabilities only after reviewing their security implications.
