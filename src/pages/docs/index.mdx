# Get started with LocalCloud

This tutorial installs the LocalCloud CLI, starts a persistent local instance, configures this shell, and verifies a Cloud Storage request. LocalCloud emulates bounded development workflows; always run final validation against real Google Cloud before production deployment.

## Prerequisites

- Docker Desktop, Colima, or Docker Engine is installed **and running**.
- A supported native CLI host: macOS 13+ or Linux with glibc 2.35+, on ARM64 or AMD64.
- `curl`, `tar`, `sed`, `sort`, and either `sha256sum` or `shasum`.

The standalone CLI is a frozen executable and does not require Python. Windows users should use the [manual Docker fallback](#manual-docker-path).

## Install the CLI

<CodeTabs labels={["Install script", "Homebrew"]}>
  <Fragment slot="tab-0">

```bash
curl -fsSL https://local.cloud/install.sh | sh
```

  </Fragment>
  <Fragment slot="tab-1">
```bash
brew install LocalGCloud/tap/localcloud
```
  </Fragment>
</CodeTabs>

The install script downloads the appropriate macOS or Linux release, verifies its SHA-256 checksum, validates the exact archive members, and runs the executable to confirm its semantic version. Release automation separately publishes Sigstore bundles, but `install.sh` does not verify those bundles.

In an interactive terminal, the installer can offer to run diagnostics and start LocalCloud after you confirm. In automation or with `--no-start`, it prints absolute-path next steps instead. If it adds the CLI to your shell startup file, run the exact `source` command printed by the installer before continuing.

</Callout>

## Start your first instance

<Steps>
  <Step title="Check Docker">

```bash
localcloud doctor
```

A usable Docker installation returns JSON with `"status": "ok"`. `doctor` diagnoses Docker; it does not install or start Docker Desktop, Colima, or Docker Engine.

  </Step>
  <Step title="Start LocalCloud">

```bash
localcloud start
```

A successful command returns `started`, `already_running`, or `reconfigured`. By default the CLI uses:

- instance `default`
- project `local-gcp-project`
- caller `local-developer`
- persistent data in the Docker volume `localcloud-data`
- Docker socket access **off**
- transparent networking **off**

The CLI binds published ports to `127.0.0.1`. If a canonical port is occupied, it can dynamically remap host ports. Use the URL and `sdk_env` values in the command output rather than assuming the console is always on port 24080.

  </Step>
  <Step title="Configure this shell">

```bash
eval "$(localcloud env)"
```

`localcloud env` inspects the running instance and prints local-only SDK settings using the actual mapped ports. It rejects environment values that would route supported services to real Google endpoints or non-loopback HTTP endpoints.

  </Step>
  <Step title="Open the console">

```bash
localcloud console
```

The CLI opens the console for the selected instance, project, and caller. Trust the returned `url`; do not replace it with a hard-coded port.

  </Step>
</Steps>

## Make your first API call

Install the Python Cloud Storage client if needed, then run this repeatable example in the same shell where you evaluated `localcloud env`:

```bash
python -m pip install google-cloud-storage
```

```python
from google.api_core.exceptions import NotFound
from google.cloud import storage

client = storage.Client(project="local-gcp-project")
bucket = client.bucket("localcloud-quickstart")

try:
    bucket.reload()
except NotFound:
    bucket.create()

blob = bucket.blob("hello.txt")
blob.upload_from_string("Hello, LocalCloud!")
print(blob.download_as_text())
```

The example safely reuses the same local bucket and overwrites the same object, so it can run repeatedly with the default persistent volume. The expected output is:

```text
Hello, LocalCloud!
```

If the SDK tries to contact Google Cloud, stop instead of adding real credentials. Re-run `eval "$(localcloud env)"` in the shell or process that launches the application. This example is source-validated and designed to be idempotent; no qualified assembled image was available in this worker environment for an end-to-end runtime execution.

## Verify and manage the instance

```bash
localcloud status
localcloud logs --tail 50
```

`localcloud stop` stops the default persistent instance but retains its volume. Running the installer with `--uninstall` removes only a script-managed CLI and its PATH block; containers and persistent volumes remain intact.

## Manual Docker path

Use this fallback on unsupported CLI hosts or when you deliberately do not want the host CLI. This starts the runtime using the image identity reviewed from `../localcloud`; its assembled digest remains release-unverified.

```bash
docker volume create localcloud-data

docker run -d --name localcloud \
  -p 127.0.0.1:24080-24092:24080-24092 \
  -m 4g \
  -v localcloud-data:/var/lib/localcloud \
  jaysen2apache/localcloud:latest
```

Verify the runtime and configure the shell through root operator endpoints:

```bash
curl -fsS http://localhost:24080/health
eval "$(curl -fsS 'http://localhost:24080/env?format=shell')"
```

The default command does not mount `/var/run/docker.sock` and does not expose ports on every host interface. GKE, Compute Engine, Cloud Run, and Dataproc execution can require explicit Docker-socket access; transparent DNS/HTTPS routing is also opt-in. Configure those capabilities only after reviewing their security implications.
