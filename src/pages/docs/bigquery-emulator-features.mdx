# BigQuery emulator feature reference

LocalCloud packages a native **GoogleSQL Analyzer** and **DuckDB** query engine. Supervisord manages the BigQuery process inside the LocalCloud Docker container. Running LocalCloud requires Docker; the default BigQuery process does not need a Docker-socket mount. An optional custom BigQuery image uses a companion container and requires Docker access.

<Callout type="warning" title="Test the image you run">
Pin an image digest and test the exact image and client you use. The `latest` tag is mutable, so a successful dry run or metadata call does not prove that a query will run.
</Callout>

## Connection and endpoints

| Surface | Canonical endpoint | Boundary |
| --- | --- | --- |
| REST API | `http://localhost:5388` | BigQuery dataset, table, job, and query routes. |
| Storage API | `localhost:5389` | Separate gRPC listener with TLS; configure the Storage client and trust the LocalCloud CA. |
| Environment export | `BIGQUERY_EMULATOR_HOST=http://localhost:5388` | Use the actual value from `localcloud env`; some SDKs need explicit client options. |
| Gateway proxy | `http://localhost:5380/bigquery/v2/` | Gateway authentication and routing differ from direct listeners. |
| Persistence | `/var/lib/localcloud/bigquery-data` | DuckDB and metadata beneath the mounted LocalCloud data volume. |

The CLI may remap host ports. The [Python SDK example](/docs/sdk-examples/#bigquery-deterministic-query) passes the generated REST endpoint explicitly and uses anonymous credentials. A REST client configuration does not configure the Storage API client.

## Validate a data pipeline locally

1. Follow the [deterministic query example](/docs/sdk-examples/#bigquery-deterministic-query) to configure the REST client, then create an owned dataset and tables with small, known fixtures.
2. Run the application's query, script, or stored procedure. Assert exact rows, column types, null handling, and expected errors.
3. For external tables, upload a CSV, JSONL, Parquet, Avro, or ORC fixture to local Cloud Storage and query it. Check the returned data instead of relying on stored connection metadata.
4. If the pipeline uses Storage Read/Write, configure its separate gRPC endpoint and CA trust, then verify Avro or Arrow records through that client.
5. Delete the owned dataset and Storage fixtures after the test. Keep application cases in the suite so future image updates run the same assertions.

The [BigQuery workflows](/services/bigquery/#workflows) cover query, job, security, BQML, Vector Search, and metadata scenarios. Check exact SQL, model, geography, and connector inputs against the features with limits below.

To weigh LocalCloud against standalone emulators and real BigQuery, see [BigQuery emulator alternatives](/compare/bigquery-emulator-alternatives/).

### Anything not listed

Anything not listed on this page is untested. Run your own queries first. A successful dry run, stored configuration or metadata call does not prove that a query will execute, and syntax, model variants, external sources, collation and individual API methods can all have gaps.

### How to check a feature

1. Confirm the exact operation and input shape your application uses against this page.
2. Pin the image digest and run your queries or API workflow. Assert the results and errors.
3. Restart the runtime and re-check if you rely on persistent state.
4. Validate production behavior in Google Cloud, in a separate environment.

## Runtime and production boundaries

Data and metadata live beneath the mounted BigQuery data directory. Verify the application's queries after restart; a mounted volume alone is not a recovery guarantee.

Ingestion-time partition pseudocolumn reads, nested policy tags, and native Bigtable, Sheets, HTTP and local-file external sources are unavailable. Validate production IAM, billing, quotas, reservations, managed integrations and recovery in Google Cloud.
