# LocalCloud vs Individual Google Emulators

Google provides official emulators for some GCP services — Pub/Sub, Firestore, and Spanner. LocalCloud bundles these with additional services into a single Docker container. Here's how the two approaches compare for local GCP development.

## Quick Comparison

| Criteria | Individual Google Emulators | LocalCloud |
|----------|---------------------------|------------|
| **Services covered** | 3 (Pub/Sub, Firestore, Spanner) | 20+ (Storage, BigQuery, Bigtable, Memorystore, Workflows, and more) |
| **Setup time** | 30+ minutes (install each separately) | < 1 minute (single Docker pull + run) |
| **Environment variables** | Set 3+ individually per service | One curl command exports all |
| **Service health check** | Check each emulator's port manually | Built-in console at localhost:8080 |
| **Seed data** | Manual per emulator | Unified seed data support |
| **Web console** | None (terminal only) | Built-in browser console for inspecting data and status |
| **BigQuery** | No official emulator exists | Custom DuckDB-based emulator (~96% SQL coverage) |
| **Bigtable** | No official emulator exists | Custom emulator with change streams, materialized views |
| **Cloud Storage** | No official emulator exists | Integrated third-party emulator |
| **Terraform** | Not supported | Full Terraform provider integration |
| **CI/CD integration** | Configure each emulator as separate service | Single service container in pipeline config |
| **Cost** | Free | Free for individual developers |

## Detailed Breakdown

### Setup Complexity

**Individual emulators** require you to install and manage each one separately:

```bash
# Pub/Sub emulator
gcloud components install pubsub-emulator
gcloud beta emulators pubsub start --project=test-project --host-port=localhost:8085

# Firestore emulator
gcloud beta emulators firestore start --host-port=localhost:8086

# Spanner emulator
gcloud components install spanner-emulator
gcloud emulators spanner start --host-port=localhost:9010
```

Each emulator runs as its own process. You manage three (or more) terminal windows. Environment variables must be set individually. Restarting your machine means rerunning everything.

**LocalCloud** is a single command:

```bash
docker run -d -p 8080:8080 -p 4443:4443 -p 8085-8087:8085-8087 \
  -p 9010:9010 -p 9020:9020 -p 9050:9050 -p 9060:9060 \
  -p 6379:6379 -m 4g --name localcloud \
  -v ~/.localcloud/data:/var/lib/localcloud \
  jaysen2apache/localcloud

eval "$(curl -s http://localhost:8080/_localcloud/env?format=shell)"
```

One container, one command, all services ready.

### The BigQuery Gap

This is the most significant difference. **Google does not provide a BigQuery emulator.** Teams developing against BigQuery have historically had two bad options:

1. **Develop against real BigQuery** — pay for every query during development, deal with network latency, risk accidental costs
2. **Don't test BigQuery code locally** — ship untested queries and hope they work in production

LocalCloud's custom BigQuery emulator (backed by DuckDB) provides ~96% SQL coverage across DQL, DDL, and DML, with 200+ mapped functions, full scripting support, INFORMATION_SCHEMA views, and both REST and gRPC Storage APIs. Teams can develop and test BigQuery workflows locally before deploying.

### Environment Management

**Individual emulators:** Each has its own environment variable name and port. You set them manually:

```bash
export PUBSUB_EMULATOR_HOST=localhost:8085
export FIRESTORE_EMULATOR_HOST=localhost:8086
export SPANNER_EMULATOR_HOST=localhost:9010
```

If you add or remove services, you update these manually.

**LocalCloud:** One command discovers and exports all variables:

```bash
eval "$(curl -s http://localhost:8080/_localcloud/env?format=shell)"
```

This sets `STORAGE_EMULATOR_HOST`, `PUBSUB_EMULATOR_HOST`, `BIGQUERY_EMULATOR_HOST`, and every other service variable in one shot. Adding services? Just restart the container with the new ports — the env export automatically picks up everything.

### Operational Visibility

Individual emulators give you terminal output. That's it. You check service health by curling ports or reading logs.

LocalCloud includes a built-in web console at `http://localhost:8080` that shows:
- Service health status for every running service
- Data browser for inspecting tables, buckets, topics
- Query interface for BigQuery and Spanner
- Configuration viewer for current settings

### Terraform Support

Individual emulators don't integrate with Terraform — you provision resources through SDK calls or command-line tools.

LocalCloud accepts standard Google provider Terraform configurations. Point the provider at LocalCloud and `terraform apply` provisions resources locally:

```bash
eval $(curl -s 'http://localhost:8080/_localcloud/env?format=terraform')
terraform init && terraform apply
```

Your `.tf` files work unchanged. Switch to real GCP by removing the env override.

## When to Use Individual Emulators

Individual Google emulators make sense when:
- You only need **one or two services** (e.g., just Pub/Sub for a messaging-focused app)
- You want the **highest fidelity** for those specific services (official emulators match production most closely)
- You're comfortable managing infrastructure manually

## When to Use LocalCloud

LocalCloud is the better choice when:
- Your app uses **3+ GCP services** and you want one boot path
- You need **BigQuery, Bigtable, or Cloud Storage** locally (no official emulators exist)
- You want a **web console** for inspecting data and service health
- You use **Terraform** and want to test configurations locally
- You want **CI/CD integration** with a single service container
- You're a **team** that wants one environment setup command instead of per-service instructions
