# LocalCloud in GitHub Actions

Run existing Google Cloud application tests against LocalCloud emulator endpoints in GitHub Actions. Keep the application's standard SDKs and native test tools.

The [setup Action](https://github.com/agent-local-cloud/setup-localcloud) starts the Docker image, waits for selected services, prepares a local project, exports SDK settings and cleans up its owned runtime. No CLI installation is needed.

## Choose a workflow

Start with the [existing-project recipe](#integrate-an-existing-project) or [workflow example](#quick-start-run-a-pull-request-test). Other routes are below.

| Route | Who starts the image? | Who configures SDKs? | Who removes the container? |
| --- | --- | --- | --- |
| Setup action | The action | The action exports runtime settings | The action's post-job hook |
| GitHub service container plus setup action | GitHub | The action connects to your service | GitHub |
| GitHub service container without setup action | GitHub | Your workflow reads the runtime settings | GitHub |

All examples below run application code on an Ubuntu VM runner. The image has a 4 GiB memory limit; allow additional memory and disk for your application. Automatic setup currently targets Linux Docker runners. A job with `container:` uses different networking and needs separate workflow tests; see [container jobs](#container-jobs-and-running-code-inside-the-image).

## Integrate an existing project

LocalCloud supplies emulator endpoints for the project's existing Google Cloud SDKs and tools. Start with a small CI/configuration change:

1. Find the existing cloud clients, test commands, lockfiles, bootstrap and emulator settings. Keep working emulators and their endpoints; for example, retain the existing Storage emulator and select only `bigquery` for missing BigQuery coverage.
2. Add the setup action before the existing service tests, preferably inside their current job. Select only the services those tests exercise. Keep the repository's dependency installation, language versions, test selection and assertions.
3. Inherit the exported SDK endpoints and project. Some clients require explicit endpoint, plaintext or local-credential options; change only the existing client/test initialization needed for that connection. Keep production defaults unchanged and fail clearly if a required local endpoint is missing.
4. Run the existing tests and required lint/regression checks. Tests must exercise the application's clients and verify their results; a new standalone SDK smoke test is not a replacement for the suite. Missing existing coverage is a reason to discuss scope, not to add an external test harness.
5. Let the Action remove its owned runtime after the job. Keep any existing emulator lifecycle intact. Preserve logs/results using the repository's existing artifact convention.

Do not bundle unrelated production fixes, scheduler changes, new dependencies, test cases, copied CI matrices or LocalCloud-specific launcher/parser scripts into an integration. Keep SDK and tool versions from the repository's own CI.

## Quick start: run a pull-request test

This example assumes the repository already uses Python 3.12, a committed `requirements.txt` and `tests/integration/`. Substitute its existing locked installation and test commands; do not create these files just to match the example. To extend an existing job, add only the Start LocalCloud step before its existing tests, and keep that workflow's name and triggers.

For a new standalone workflow, use the display name `pr-local-cloud-integration-tests`. Save the following as `.github/workflows/localcloud.yml`, adapting event/branch/path filters to the repository's normal CI:

```yaml
name: pr-local-cloud-integration-tests
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  integration:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7.0.1
      - uses: actions/setup-python@v7.0.0
        with:
          python-version: '3.12'
      - name: Install existing dependencies
        run: python -m pip install -r requirements.txt
      - name: Start LocalCloud
        id: localcloud
        uses: agent-local-cloud/setup-localcloud@3f8bd6df58cfd3cf4cd29c46f3449c7e6465f64a
        with:
          image: agentcloud/localcloud:ci
          console: 'false'
          services: bigquery
          project-id: localcloud-ci
      - name: Run existing integration tests
        run: python -m pytest tests/integration/
```

The example selects only BigQuery. Replace `services` with the set actually exercised by your tests; no Google Cloud credentials or billing project are needed for LocalCloud calls. The Action exports local SDK settings to subsequent steps in this job, waits for readiness and removes its own runtime after success or failure. It does not rewrite the application's client constructors or test selection.

### Triggers and repository security

Use normal CI triggers without adding `LOCALCLOUD_CI_ENABLED` or another LocalCloud-specific enable flag. Preserve repository-specific branch/path filters, main-repository restrictions, approval labels and required checks. Those controls are repository policy, not universal LocalCloud prerequisites; do not copy another project's hard-coded owner or label names. A skipped or approval-blocked job is not passing test evidence.

Prefer the existing unprivileged `pull_request` workflow. Do not switch to `pull_request_target` just to bypass fork approval. If the repository already requires a trusted-context workflow, follow its approved-code policy, apply its guard to every job, keep permissions minimal and use an explicitly reviewed checkout strategy. Fork-origin PRs targeting the upstream repository and workflows hosted inside a fork are different cases.

GitHub may separately require a maintainer to approve a fork's workflow execution. That approval is distinct from a PR review or a repository label. Runs awaiting approval for more than 30 days expire as failed without running tests; see [GitHub's fork-run approval guide](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks).

## Validate a staging build

Each job starts a fresh runtime for application tests before staging deployment. Save this as `.github/workflows/staging-validation.yml`; adapt `requirements.txt` and `tests/integration/` to your repository. Test fixtures should create representative resources through the [SDKs](/docs/sdk-examples/).

```yaml
name: Validate staging build
on:
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
jobs:
  staging-check:
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7.0.1
      - uses: actions/setup-python@v7.0.0
        with:
          python-version: '3.12'
      - name: Start the test environment
        uses: agent-local-cloud/setup-localcloud@3f8bd6df58cfd3cf4cd29c46f3449c7e6465f64a
        with:
          image: agentcloud/localcloud:ci
          console: 'false'
          services: gcs,pubsub,bigquery
          project-id: localcloud-staging
      - run: python -m pip install -r requirements.txt
      - name: Run application integration tests
        run: python -m pytest tests/integration/ --junitxml=localcloud-results.xml
      - name: Save test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: localcloud-staging-results
          path: localcloud-results.xml
          if-no-files-found: ignore
```

Gate a subsequent deployment job with `needs: staging-check`; use GitHub [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) for its approvals and secrets. This job needs no Google Cloud credentials. LocalCloud lasts for the job; validate managed IAM, networking, quotas, and performance against real Google Cloud staging before production.

For persistent environments, use [existing-runtime mode](#use-a-native-github-service-container) with owner-managed state. Other languages keep their native tools and [SDK configuration](#configure-your-applications-sdks).

## Select the services your application needs

`services` is the exact comma-separated set to start. It replaces the default selection; include every service your test needs. It accepts LocalCloud service IDs, not Google API domain names or display names.

```yaml
- uses: agent-local-cloud/setup-localcloud@3f8bd6df58cfd3cf4cd29c46f3449c7e6465f64a
  with:
    image: agentcloud/localcloud:ci
    console: 'false'
    services: gcs,pubsub,bigquery,bigtable,spanner,kms,secretmanager
    project-id: localcloud-ci
    timeout: '180'
```

Always set it explicitly; the default is `gcs,pubsub,bigquery`. Firestore is supported; select `firestore` when your tests need it and allow memory for its runtime.

### Docker-backed execution

By default the action sets `LOCALCLOUD_DOCKER_ACCESS=false` and mounts no Docker socket, so selecting `cloudrun`, `dataproc`, or `gke` alone does not configure their execution. Set [`docker-access`](#image-reuse-container-applications-and-mcp) for native execution on the runner, or connect to a provisioned runtime with `runtime-url`.

## Pin the action and runtime independently

Examples use the reviewed full Action commit shown in the workflow, which supports the CI image channel and `console` input. Use a reviewed full Action commit; keep the repository's other Action/toolchain pins. Older release tags may describe an earlier input/default contract.

Set `image: agentcloud/localcloud:ci` for normal CI. Each new owned runtime pulls the current tag, reusing unchanged layers; the Action commit stays pinned. Record `image-digest` for diagnosis. Image updates must retain compatible runtime/SDK contracts; the moving tag does not promise identical behavior across releases.

For a controlled reproduction you can supply `agentcloud/localcloud@sha256:<digest>` from a prior run, but a permanent runtime digest is not the default integration recipe. The Action accepts `:ci` or a digest; arbitrary version, `latest` and `lite` tags are not accepted by this Action revision. OCI `image-cache` needs a digest-pinned input, so omit it when following the moving CI channel.

| Action input | How to use it |
| --- | --- |
| `services` | Set the complete comma-separated ID list explicitly. |
| `project-id` | Local project to create or select; default `localcloud-ci`. |
| `image` | `agentcloud/localcloud:ci` for normal CI; an `@sha256:` identity for a controlled reproduction. Used only when the Action starts Docker. |
| `console` | Default `'false'`; keep it explicit for API-only CI. Applies only to an Action-owned runtime. |
| `timeout` | Selected-service readiness wait in seconds; default `120`, range `1`–`1800`. |
| `runtime-url` | Leave empty for automatic startup, or supply an existing local HTTP gateway. Use `port-map` when listeners are remapped. |

## Headless CI

Use `console: 'false'` for an Action-owned runtime; readiness and service APIs remain available. For service/direct Docker containers, set `LOCALCLOUD_CONSOLE=false` on the owner. The CLI equivalent is `localcloud start --no-ui`.

Console off does not reduce image download size or establish a startup-speed claim. Attaching the Action never upgrades an existing runtime or changes its Console.

## Use a native GitHub service container

If you want GitHub to start and stop the image, declare it under `jobs.<job>.services`. The setup action can configure that existing runtime without taking ownership of it. Save this as a separate workflow:

```yaml
name: pr-local-cloud-integration-tests
on: [pull_request, workflow_dispatch]
permissions:
  contents: read
jobs:
  integration:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    services:
      localcloud:
        image: agentcloud/localcloud:ci
        env:
          LOCALCLOUD_SERVICES: gcs,pubsub,bigquery
          LOCALCLOUD_PROJECT: localcloud-ci
          LOCALCLOUD_TELEMETRY: 'false'
          LOCALCLOUD_DOCKER_ACCESS: 'false'
          LOCALCLOUD_CONSOLE: 'false'
        ports:
          - 5380:5380
          - 5382:5382
          - 5383:5383
          - 5388:5388
        options: --memory 4g
    steps:
      - uses: actions/checkout@v7.0.1
      - uses: actions/setup-python@v7.0.0
        with:
          python-version: '3.12'
      - name: Configure the existing runtime
        uses: agent-local-cloud/setup-localcloud@3f8bd6df58cfd3cf4cd29c46f3449c7e6465f64a
        with:
          runtime-url: http://127.0.0.1:5380
          services: gcs,pubsub,bigquery
          project-id: localcloud-ci
      - run: python -m pip install -r requirements.txt
      - run: python -m pytest
```

This alternative assumes existing `requirements.txt` and pytest tests; substitute the repository's native commands. Automatic Action startup is simpler when an existing service-container convention does not need to be retained. Keep the container's service selection and the action's selection aligned. Publish any additional listeners your tests need; BigQuery Storage gRPC, for example, also needs port 5389.

With an existing runtime, `runtime-url` identifies the reachable gateway and `port-map` explicitly maps canonical service ports to their published ports. Preserve those mappings; automatic startup already exports remapped SDK endpoints. The `image` and `console` inputs do not replace or reconfigure an attached runtime: set `LOCALCLOUD_CONSOLE=false` on its owning service/container, as above. GitHub removes its service containers at the end of the job. See GitHub's [service container documentation](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers).

## Use the image without the action or CLI

Prefer automatic setup unless another platform or an existing container owner needs direct control. Keep the service declaration above, including `agentcloud/localcloud:ci` and `LOCALCLOUD_CONSOLE=false`. Its owner must:

1. Wait for `/readiness?services=gcs,pubsub,bigquery` to report every selected service ready.
2. Create/select its isolated project through `/projects`.
3. Read `/env?format=json&project=localcloud-ci`, validate the expected project and local SDK origins, and export only the required settings to the test process. Map published ports explicitly; never fall back to Google endpoints.
4. Run the repository's native tests and clean up only its owned runtime/state.

The [Action repository's direct-image check](https://github.com/agent-local-cloud/setup-localcloud/blob/3f8bd6df58cfd3cf4cd29c46f3449c7e6465f64a/.github/workflows/guide.yml) contains the complete three-service bootstrap. Other service sets need their corresponding listeners and SDK settings. Reuse an existing owner/bootstrap; do not add this control-plane harness to an otherwise one-step Action integration. See the [runtime API](/docs/architecture/) and [manual Docker setup](/docs/#manual-docker-path).

## Configure your application's SDKs

The setup action exports values returned by `/env?format=json` into `GITHUB_ENV`. They are available to subsequent steps, including your test process or agent process. Do not hard-code ports in automatic mode.

| Client | Configuration |
| --- | --- |
| Python Cloud Storage | Reads `STORAGE_EMULATOR_HOST`; pass the local project to `storage.Client`. |
| Python Pub/Sub | Reads `PUBSUB_EMULATOR_HOST`; construct the usual publisher/subscriber clients. |
| Python BigQuery | Pass `BIGQUERY_EMULATOR_HOST` explicitly as `client_options.api_endpoint` and use `AnonymousCredentials` for the local client; preserve normal production credentials outside local-test mode. |
| Java Pub/Sub | Configure the exported `PUBSUB_EMULATOR_HOST` explicitly with a plaintext gRPC channel and a no-credentials provider for both publisher and subscriber clients. |
| Other languages and services | Use the service guide and SDK examples; some need an explicit endpoint, plaintext transport, or local credentials. |

See [copyable SDK examples](/docs/sdk-examples/) for resource creation, readback, and cleanup. Environment-variable export does not guarantee every Google SDK automatically consumes every setting. Keep missing endpoint variables as errors instead of silently choosing Google defaults. Local tests do not need production Google credentials.

## Run an AI coding agent in the job

Start LocalCloud before installing and launching your agent on the same runner. It inherits the SDK environment. Authenticate the AI provider separately, following your agent's instructions.

Give the agent these repository instructions:

```text
Use this job's GOOGLE_CLOUD_PROJECT and local SDK endpoints. Follow the
LocalCloud service guides and run application tests. Do not start another
runtime, request Google credentials, or fall back to real Google Cloud.
```

For another container, forward the environment and use reachable service addresses rather than host loopback. Provide the [agent guide](/ai/agents.md) and [service reference](/ai/services.md) as context.

### Optional MCP

SDK tests don't need MCP. The `mcp:` input adds a job-local MCP bridge, as [described below](#attach-an-mcp-client). See the [MCP guide](/docs/mcp/) for clients and separate write and destructive permissions.

## Container jobs and running code inside the image

With `container:`, native services use their service name and internal ports, such as `http://localcloud:5380`; test connectivity and SDK configuration for that network.

To run code inside LocalCloud, preserve its entrypoint, wait for readiness, and provision your toolchain before `docker exec`. Build tools are not guaranteed to be bundled. See [manual Docker setup](/docs/#manual-docker-path) and the [application-container route](#run-an-application-container).

## Troubleshooting and cleanup

| Symptom | Next check |
| --- | --- |
| Readiness times out | Check the selected IDs, runtime logs, image version, memory, and the service's execution dependencies. A container being up does not prove readiness. |
| Unknown service | Use an exact ID from the table; a catalog entry marked Unsupported does not run locally. |
| SDK asks for Google credentials | Verify local endpoint variables and the client-specific constructor; Python BigQuery requires explicit anonymous credentials. |
| Application calls a Google endpoint | Check hard-coded URLs and client configuration. The action configures endpoints; it is not an egress firewall. |
| Native service connects but SDK calls fail | Publish the selected service ports and supply `port-map` when their host ports differ. |
| Agent runs in another job or container | Export settings again for that environment and verify its network route; `GITHUB_ENV` is job-scoped. |
| Job is skipped or has no test logs | Inspect event filters, job conditions, approval labels and fork-run approval. An expired approval is a workflow-execution outcome, not a test failure. |
| One platform times out in an existing test | Compare the failing phase and upstream baseline, then rerun only that job with a maintainer if permitted. Keep assertions, timeouts and test selection intact while diagnosing. |
| Self-hosted runner loses a job | Inspect action-owned containers and volumes. Normal post cleanup is best effort when a runner disappears; do not delete unrelated developer resources. |
| Docker pull reports `toomanyrequests` | The registry rejected the pull before LocalCloud started. Authenticate to Docker Hub as described below, connect to an already-running runtime through `runtime-url`, or select a compatible registry image through `image`. |

Post cleanup removes Action-owned resources after success or failure. Cache dependencies separately from runtime data. If a self-hosted runner disappears, recover only resources identified by its ownership receipt; avoid broad Docker pruning.

Automatic mode creates an isolated container and anonymous data volume. Logical project names in a shared existing runtime are not a hard isolation boundary. Parallel jobs should use independent runtimes unless shared state is intentional.

### Docker Hub pull limits

Public Docker Hub images can hit anonymous pull limits on shared CI runners. If this happens, store your Docker Hub username and access token as repository secrets named `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`. These are image-registry credentials, separate from Google Cloud credentials.

For action-managed Docker, place this step before Setup LocalCloud:

```yaml
- name: Authenticate image pulls
  env:
    DOCKERHUB_USERNAME: ${{ secrets.DOCKERHUB_USERNAME }}
    DOCKERHUB_TOKEN: ${{ secrets.DOCKERHUB_TOKEN }}
  run: printf '%s' "$DOCKERHUB_TOKEN" | docker login --username "$DOCKERHUB_USERNAME" --password-stdin
```

Native service containers start before workflow steps, so a login step is too late for their initial pull. Add this mapping to `jobs.<job>.services.localcloud`, alongside `image`:

```yaml
credentials:
  username: ${{ secrets.DOCKERHUB_USERNAME }}
  password: ${{ secrets.DOCKERHUB_TOKEN }}
```

GitHub documents [service-container registry authentication](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers#authenticating-with-image-registries).

## Image reuse, container applications and MCP

The pinned Action in this guide also supports application-container networking, image reuse and a job-local MCP bridge. These are optional; ordinary SDK tests do not need them.

```yaml
- name: Start the CI environment
  id: localcloud
  uses: agent-local-cloud/setup-localcloud@3f8bd6df58cfd3cf4cd29c46f3449c7e6465f64a
  with:
    image: agentcloud/localcloud:ci
    console: 'false'
    services: gcs,pubsub,bigquery
    project-id: localcloud-ci
    mcp: 'true'
```

| Input | Usage |
| --- | --- |
| `image-cache` | Path to a restored OCI image layout; needs a digest-pinned `image`. The action verifies the requested digest, selected platform and image blobs before importing it. Omit for ordinary Docker image reuse. |
| `port-map` | JSON canonical-to-published port mapping for an existing HTTP runtime, such as `{"5380":15380,"5382":15382,"5383":15383,"5388":15388}` with `runtime-url: http://127.0.0.1:15380`. Include every selected endpoint that uses a remapped listener. |
| `docker-access` | Explicitly set `'true'` for native Dataproc, Cloud Run or GKE execution. This mounts the runner's Docker socket and grants the runtime Docker host access. Keep it off for ordinary SDK tests. The runtime reports its own prerequisite requirements. |
| `control-token` | The runtime's `LOCALCLOUD_CONTROL_TOKEN` (32+ characters), needed when its remote access is on. Masked in logs. |
| `mcp` | Set `'true'` to generate a job-local read-only MCP configuration attached to this runtime and project. No CLI or second runtime is installed. |

### Reduce image pulls

A digest-pinned image is reused if present locally; `ci` is always pulled, reusing cached layers. Persistent Docker runners can reuse that image across jobs; each job still creates fresh application state. Standard GitHub-hosted runners start fresh, so they need a restored cache or registry distribution for reuse across jobs.

The action's [cache workflow](https://github.com/agent-local-cloud/setup-localcloud/blob/main/.github/workflows/cache.yml) shows how to create and restore a verified OCI cache. Cache keys include the exact image and platform; do not cache credentials or application data. Measure restore/import time before enabling it widely. Native service images start before cache/login steps. For fork PRs, use a public image or a trusted restore-only cache because ordinary repository secrets are unavailable.

### Run an application container

The action exports `network` and `docker-env-file` outputs for its owned runtime. Start an application container on that network and pass the environment file:

```yaml
- name: Test an application image
  env:
    LOCALCLOUD_NETWORK: ${{ steps.localcloud.outputs.network }}
    LOCALCLOUD_ENV_FILE: ${{ steps.localcloud.outputs.docker-env-file }}
  run: docker run --rm --network "$LOCALCLOUD_NETWORK" --env-file "$LOCALCLOUD_ENV_FILE" my-application-tests
```

Build the test image with your dependencies. These settings use internal service addresses; runner loopback addresses cannot reach LocalCloud from another container. The action removes its owned runtime, volume, execution children, and network. Use `--rm` and failure cleanup for application containers you launch. Existing runtimes retain their owner's lifecycle. On interrupted self-hosted runners, recover only resources identified by the job's ownership labels and receipt.

### Attach an MCP client

With `mcp: 'true'`, pass `steps.localcloud.outputs.mcp-config` to a client supporting a `mcpServers` configuration. The generated stdio bridge targets the same gateway and project as the SDK environment. It leaves global client settings untouched and keeps runtime MCP writes and destructive operations disabled; ordinary SDK writes are governed separately by the application's client configuration and runtime IAM mode.

For native container jobs, use the service-name gateway and explicitly permit MCP traffic on that isolated job network in the service environment with `LOCALCLOUD_MCP_ALLOW_REMOTE: 'true'`. Keep both `LOCALCLOUD_MCP_WRITE` and `LOCALCLOUD_MCP_DESTRUCTIVE` false. Do not expose that service publicly.

Remote access turns on LocalCloud's control token: set `LOCALCLOUD_CONTROL_TOKEN` on the service (for example from a secret) and pass the same value as the action's `control-token`.
