# Select correctness checks by change

Read current `AGENTS.md`, `BUILD.md`, `package.json`, and the deployment guide from the repository root. They own command definitions and release mechanics; this matrix adds the reasons and behavior to verify. Select all rows touched by shared code.

| Change | Correctness questions | Additional verification |
| --- | --- | --- |
| Capability or service documentation | Does the fact match committed runtime/CLI evidence? Are defaults separate from support? Do compatibility, service, and agent surfaces agree without repeating whole workflows? | Upstream sync + strict verification for a refresh; distributed-doc verifiers; build's contract/examples/content-facts checks. If siblings are absent and parity skips, run parity where available or report it unverified. |
| SDK/CLI examples | Do exports point to local endpoints using the right transport/client settings? Are install/setup requirements clear? Does the example assert its advertised result and clean up writes? Is an empty list correctly described? | Existing example verifier and supported language compile/execution checks. Record whether checks are static, compilation, or actual SDK execution; do not infer runtime success from the build. |
| New or renamed page/blog | Is content present in static HTML? Are title, description, canonical, social image, structured data, sitemap, internal links, anchors, search, and applicable Markdown twin correct? Does a removed public URL redirect? | Build's SEO/content/blog checks; `test:links`, `test:blog`, `test:sitemap-guard`, `test:live-seo` as affected. Browse rendered pages and search results. Do not fabricate review/rating data for optional schema warnings. |
| Layout, theme, code panel, shared component | Are intended views/audiences styled correctly? Is text legible, focus visible, accessible naming consistent with visible labels, and the content usable on narrow screens? Do copy controls avoid blank-line padding or covering code? | `test:performance`; browser desktop/mobile and affected Desktop/Classic/human/agent combinations. Check keyboard use, code tabs, long content, overflow, and remounts. |
| Dialog, menu or popup | Does a modal move/contain/restore focus and make the background inert? Do Escape and the visible close control work? Do appropriate popups dismiss on outside click, focus departure or another popup opening? Are visible and accessible labels consistent? | `test:performance` includes the real-browser interface regression. Exercise both pointer and keyboard flows, reopen controls, and check the 320px layout. Prefer native dialogs and shared popup handlers. |
| Navigation or audience persistence | Does direct entry work? Do search and links retain the correct view/audience? Do Back/Forward, fragments, unrelated query parameters, remounts, and remembered preferences work? Does the shell remain stable in existing in-place flows? | `test:performance`, especially navigation/agent-mode tests; browser checks with a clean preference state and remembered-agent state. Confirm human startup keeps agent-only code lazy. |
| “My cloud” / localhost readiness | Can running, stopped, slow, blocked, and permission-denied states be distinguished? Is browser policy being mistaken for an absent runtime? Are instructions and retry behavior usable? | Existing My cloud unit/browser checks plus a normal browser session without pre-granted localhost permission. A mocked fetch or pre-authorized browser alone missed a historical failure. Follow the current product fallback; do not infer a runtime is stopped from a generic fetch error. |
| Performance | Is the attributed cost first-party code, third-party analytics, or a small/historical field sample? Are shell repaint, forced layout, request chains, asset size, and lazy modules appropriate? | `test:performance`; fresh browser trace/lab measurement for affected route/device. Preserve budgets and analytics functionality. State sample/device/build; keep lab, CrUX and RUM results separate. |
| Analytics or privacy | Do events arrive with the correct route attribution after in-place navigation? Do consent, GPC/DNT, sampling, replay/error capture, CSP and proxy behavior still work? | `test:analytics`, affected performance tests; browser request checks and marked records in the correct project when live verification is authorized. Exclude marked records from organic metrics. Do not remove valuable analytics solely to improve an audit score. |
| Worker, CSP, headers, compression, caching | Do response bytes, status, charset, Markdown negotiation, encoding and cache headers agree? Are missing routes real 404s? Do older open pages retain needed assets? | Build first, then `test:worker`, `test:analytics`, `test:live-seo`, `test:asset-manifest`, `test:sitemap-guard` as affected. Test workerd/Worker behavior; Astro preview alone does not apply deployment headers. |
| Installer/dependencies | Are install methods, platform handling, prompts, checksum pinning, repair and configuration preservation correct? Did dependency changes alter build/runtime behavior? | Mandatory installer suite and dependency audit; affected build/Worker/performance checks. Installer fixtures do not prove real Docker/runtime startup. |
| Local development tooling | Does it activate only in the intended local environment and remain absent from production artifacts? | Existing Agentation tests and production-output exclusion verifier; exercise actual local feedback delivery if changing the integration. A devDependency declaration alone does not enforce exclusion. |
| Authorized release | Does the deployed source match the tested commit? Are current/previous assets, public routes, custom domain, crawler/agent documents, analytics and relevant browser flows working? | Complete documented release pipeline, CI results, live version/source identity, live route verifier and affected desktop/mobile flows. Report unavailable PageSpeed/dashboard checks separately. |

For a failure report, reproduce or verify the claimed problem before changing the site. A dead click on inert text is not automatically a dead link. A scanner's nonexistent URL is not a broken public route. A valid redirect or crawlable HTTP 200 does not establish search indexing. Use the observation that matches the claim.

For upstream facts, source and documentation establish intended capability. Runtime execution, image/platform qualification, published artifacts, and production deployment require their own evidence. Keep these distinctions in the acceptance record.
